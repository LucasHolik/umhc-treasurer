# PLAN: HIDE PAST TRIP/EVENT TAGS WHEN TAGGING + "COMPLETED INVESTMENT" STATUS
# Branch: claude/confident-ptolemy-0qqk7l
# Status: PLANNED (not yet implemented)

================================================================================
1. GOAL
================================================================================

  1. When tagging transactions (the tag box in the Transactions section),
     show only CURRENT Trip/Event tags by default. Tags whose status is
     "Completed" (or the new "Completed Investment") are hidden.
  2. A "See past tags" control at the bottom of the box reveals every tag,
     whatever its status. "Hide past tags" puts it back.
  3. Add a fourth Trip/Event status, "Completed Investment", so that
     investments that are still running ("Investment") can be told apart from
     ones that have finished.

Terms used below:
  CURRENT status = "Active" | "Investment"
  PAST status    = "Completed" | "Completed Investment"
  A trip with no status, or a status the app does not recognise, counts as
  CURRENT. This matches the existing "missing means Active" default, and it
  means a typo in the sheet can never hide a tag someone needs.

Only Trip/Event tags have a status (TripStatusMap). Category and Type tags
are not affected and always show in full.


================================================================================
2. WHAT CHANGES (AND WHAT DOES NOT)
================================================================================

Changes:
  - Transactions inline tag box (desktop table and mobile cards): Trip/Event
    list hides past tags, with a "See past tags" toggle.
  - Split-transaction modal tag box: same behaviour (it also tags
    transactions).
  - Bulk-tag mode "Set Trip/Event..." dropdown: same behaviour, so all three
    ways of tagging act the same.
  - Tags page: status cycle, icons, colours and legend gain
    "Completed Investment".
  - Analysis: Trip Status filter gains "Completed Investment Only".
  - Backend: accepts "Completed Investment" as a valid status.

Does NOT change:
  - Transactions FILTER bar (Category / Trip/Event checkboxes). Filtering
    covers past data, so every trip stays listed.
  - Analysis trip pickers, which are already driven by the Trip Status
    filter.
  - Tags page "Type" selector (it assigns Types to trips; Types have no
    status).
  - Pill display: a transaction already tagged with a completed trip still
    shows that tag as normal.
  - Effective Balance (analysis.logic.calculateEffectiveBalance) still counts
    "Active" trips only. Neither investment status is included, as today.
  - Sheet layout: status is still stored as text in column C of the Tags
    sheet. No migration is needed. Existing "Investment" trips stay active
    investments until the treasurer marks them "Completed Investment".


================================================================================
3. DESIGN (KEEPING TO THE SEPARATION OF CONCERNS)
================================================================================

  User Action -> Service Layer -> State (Store) -> UI Re-render

  - No new store keys and no new API calls. TripStatusMap is already in
    store.tags. The "show past tags" switch is short-lived view state inside
    one open popover, just like the selector's existing searchTerm. It resets
    every time the box opens, so it does not belong in the Store.
  - Status rules live in ONE pure module (no DOM, no store), so the UI stays
    dumb and the same rules apply in Tags, Transactions and Analysis.
  - The UI that owns the data (TransactionsComponent, SplitTransactionModal,
    TransactionsBulk) works out the current/past split with the pure helper
    and passes the two lists to the selector. The shared TagSelector only
    renders what it is given. It does not learn what "status" means.
  - Everything is still built with el(); no innerHTML.

C. FEATURE: src/features/transactions/transactions.component.js
--------------------------------------------------------------------------------
There are three near-identical this.tagSelector.show(...) calls (click on
"+", click on a pill, keyboard). Combine them into one private method:

  openTagSelector(target, rowId, type, currentVal) {
    const options = this.getTagSelectorOptions(type);
    this.tagSelector.show(target, type, currentVal,
      (newVal) => this.updatePendingChange(rowId, type, newVal),
      options.customOptions, { pastOptions: options.pastOptions });
  }

  getTagSelectorOptions(type) {
    const tags = store.getState("tags") || {};
    if (type !== "Trip/Event") return { customOptions: null, pastOptions: [] };
    const { current, past } =
      partitionTripsByStatus(tags["Trip/Event"] || [], tags.TripStatusMap || {});
    return {
      customOptions: current,
      pastOptions: past.map((t) => ({
        value: t, hint: getTripStatusStyle(tags.TripStatusMap[t]).label })),
    };
  }

  This method only arranges data the component already reads. The rules
  themselves stay in trip-status.js. Category behaves exactly as before
  (customOptions null -> selector reads the store as it does now).
