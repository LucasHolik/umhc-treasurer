================================================================================
1. SUMMARY
================================================================================

Loading data after saving tags failed or hung because the client gave up
after 20 s while the server waited up to 30 s for the script lock, and a
tag batch held that lock for its whole (slow) run. getAppData queued behind
it and, if its lock wait expired, silently returned an empty split list.

Fixed by:
  - one nest-safe lock helper with a 10 s wait (C1)
  - getAppData reading everything under one lock and failing loudly (C5)
  - 30 s read / 60 s write client timeouts, a TIMEOUT error code, reload
    coalescing and timeout-aware tag-save recovery (C2, C3)
  - sanitising every write-back of tag values, and a cheaper _addTag (C4, C6)

ACTION NEEDED: paste all .gs files (including the new Service_Lock.gs) into
Apps Script, deploy a NEW VERSION of the web app, then log out and back in
once. The frontend works against both the old and the new backend.

3. BACKEND (google-apps-script/)
================================================================================

Service_Lock.gs (NEW)
  - Service_Lock.withScriptLock(fn, timeoutMs): the only code that calls
    LockService. Waits up to CONFIG.LOCK_TIMEOUT_MS; if the lock is taken,
    returns { success: false, message: "System is busy. Please try again." }
    (same shape and message as before).
  - Nest-safe: a per-execution depth counter (_scriptLockDepth) makes an
    inner call run straight through under its caller's lock. It never waits
    on that lock or releases it early. Release happens in a finally block,
    at the outermost level only.

Config.gs
  - New CONFIG.LOCK_TIMEOUT_MS = 10000, with a comment tying it to the
    client timeouts.

Service_Sheet.gs
  - saveData, removeTagFromExpenses, restoreTagInExpenses,
    updateExpensesWithTag: hand-written lock boilerplate replaced with
    withScriptLock. restoreTagInExpenses keeps its early "No rows to
    restore" return before the lock.
  - updateExpenses: now locked as a whole (was unlocked), so
    updateSplitRowTag nests inside it. It passes the RAW tag values to
    updateSplitRowTag, which validates and sanitises them itself. Before,
    an already-sanitised "'-Misc" failed validation. updateSplitRowTag
    failures are now pushed to `failures` instead of being ignored.
  - getData: now runs under withScriptLock (was unlocked).
  - getOpeningBalance: read-only; an empty cell reads as 0 without
    writing 0.
  - saveOpeningBalance: calls _ensureConfigSheetLayout().
  - _getConfigSheet(): now read-only (creates the sheet only if missing).
  - _ensureConfigSheetLayout() (NEW): legacy B->C balance migration and
    title cells, moved out of _getConfigSheet. Returns the sheet.
  - Column rewrites (removeTagFromExpenses, updateExpensesWithTag) and
    _sortSheetByDate write back through _sanitizeGridForSheet.
    restoreTagInExpenses sanitises the restored value.

Service_Split.gs
  - processSplit, removeTagFromSplits, restoreTagInSplits,
    updateTagInSplits, updateSplitRowTag, revertSplit, editSplit,
    getSplitGroup, getSplitHistory, getAllSplitHistory: lock boilerplate
    replaced with withScriptLock. restoreTagInSplits keeps its early return
    before the lock.
  - removeTagFromSplits, updateTagInSplits, _writeSplitData (archive rows
    copied from the Finances row) and _restoreSplitData write back through
    _sanitizeGridForSheet. restoreTagInSplits sanitises the restored value.

Service_Tags.gs
  - _runTagBatch: one withScriptLock around the whole batch. Its helpers'
    locks nest inside it. (Before, every Trip/Event or Category
    rename/delete in a batch failed or dropped the batch's lock.)
  - addTag / deleteTag / renameTag (single-op entry points): now locked as
    a whole (previously unlocked or only locked piecemeal).
  - _addTag: reads the target column once for both the duplicate check and
    the first empty row. A Trip/Event's A:C cells (name, Type, "Active")
    are written in one setValues, and the Type value is sanitised. Return
    values are unchanged.
  - Sanitised writes: _sortTags output, _restoreTagSheet snapshot (string
    cells), _updateTripType, the Trip-Type column rewrites in _deleteTag
    and _renameTag, and the three rename rollbacks of the master cell.

Code.gs
  - getAppData: runs entirely under withScriptLock, so expenses, tags,
    opening balance and splits come from one moment. If any part fails, it
    logs which part and returns { success: false, message: "Error loading
    app data" }. It no longer returns splitTransactions: [] or a default
    balance or tags.
  - _sanitizeGridForSheet(values) (NEW): applies _sanitizeForSheet to every
    string cell of a getValues()-style grid before setValues. getValues()
    returns stored text without its protective apostrophe, so writing a
    grid back raw turned "-Misc" into #ERROR! and "=..." into a live
    formula, including UNTOUCHED cells of a rewritten column. Numbers,
    dates and booleans pass through. Applying it twice is harmless.

Service_Auth.gs
  - login(): calls _ensureConfigSheetLayout() (non-fatal on error) after
    the signature has been verified. getPasskeys stays read-only, so
    unauthenticated login attempts never write to the sheet.

README.md
  - Service_Lock.gs added to the paste list and the file structure.
  - New note: redeploy as a new version after changing .gs files, then log
    out and back in once (login runs the Config layout check).

4. FRONTEND (src/)
================================================================================

services/api.service.js
  - READ_TIMEOUT_MS = 30000 and WRITE_TIMEOUT_MS = 60000 replace the fixed
    20000. resolveTimeout(options) picks options.timeoutMs, else the write
    timeout for mutating requests (options.withNonce), else the read
    timeout. It is exported for the self-tests. A comment states the
    invariant against the server's LOCK_TIMEOUT_MS.
  - A timeout rejects with err.code = "TIMEOUT" (outcome unknown).
  - A network error (script onerror) rejects with err.code = "NETWORK"
    (outcome also unknown). A "System is busy" reply sets
    err.code = "BUSY".
  - A server { success: false } rejects with err.response = data, so
    tag-batch appliedOperations now reach the caller (before, they were
    always lost).

App.js
  - loadInitialData: a call that arrives while a load is running sets
    _reloadPending instead of being dropped. When the running load
    finishes, one more load runs.
  - loadInitialData does nothing without a session. The failure paths below
    always dispatch "dataUploaded", including after an "Unauthorized" reply
    has already logged the user out. Without the check, that reload replaced
    "Session expired" on the login screen with "Failed to load application
    data". The same check covers the follow-up load.
  - A failed load no longer replaces an error that is already showing
    (e.g. why a save failed); it adds its own message after it. It still
    replaces an earlier load error, so repeated refreshes don't pile up
    messages. A BUSY reply explains that the server is busy with other
    changes instead of the generic "Failed to load application data".

features/tags/tags.logic.js
  - resolveSaveFailure(queue, processedCount, chunkSize, error) (NEW, pure)
    -> { remainingQueue, exitEditMode, message }
      TIMEOUT: drop the queue and leave edit mode. The message counts the
        operations saved, the chunk whose outcome is unknown, and those
        never sent (which must be re-entered).
      NETWORK: keep every unconfirmed operation (nothing is lost). The
        message says the in-flight chunk may or may not have saved, and
        that saving again is safe: each chunk is atomic, so a chunk that
        was already applied fails ("already exists" / "not found") and
        changes nothing.
      Rejection: keep queue.slice(processedCount + appliedCount).
        appliedCount comes from err.appliedCount or
        err.response.appliedOperations.

features/tags/tags.component.js
  - handleSave and handleAddTripSave use resolveSaveFailure and always
    dispatch "dataUploaded" when a save fails, because earlier chunks may
    be committed. On TIMEOUT, handleAddTripSave returns to the details
    view.

features/transactions/transactions.component.js
  - savePendingChanges and applyBulkTags: when a save fails, also dispatch
    "dataUploaded". On TIMEOUT or NETWORK the error banner reads "... may
    not have saved (no reply from the server). Please check them once the
    data has reloaded." Unsaved edits stay pending; the reload removes only
    the ones it can see were saved.

features/settings/selftest/
  - tests.api.js: resolveTimeout read default, write default, explicit
    override.
  - tests.tags.js: resolveSaveFailure on TIMEOUT (queue dropped, edit mode
    left, saved / unknown / never-sent counts), TIMEOUT on the last chunk,
    rejection with appliedOperations, rejection with none applied, and
    NETWORK (every unconfirmed op kept pending).
